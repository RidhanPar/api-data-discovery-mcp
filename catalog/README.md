# Nordlys Insurance – synthetic API & Data Product catalog

> **Nordlys Insurance is fictional.** All APIs, teams, people, data and URLs are invented.
> Hostnames use the reserved `.example` top-level domain (RFC 2606).

This is the raw material the discovery platform indexes: **25 OpenAPI 3.1 specs** and **15 Data
Product contracts** for a Nordic and Baltic insurer (SE, NO, FI, DK, EE, LV, LT).

Run `uv run python -m nordlys_discovery.catalog` to validate every file and print the summary
numbers (counts, market coverage, deprecations, metadata gaps). Nothing in this document is
counted by hand.

## Layout

```
catalog/
  apis/<domain>/<api-id>.v<major>.yaml     # OpenAPI 3.1 – GENERATED, do not edit by hand
  data-products/<id>.yaml                  # data contracts – hand-written
```

The API specs are generated by `scripts/catalog_gen/` so they are reproducible, but every
description in the generator is written by hand per API. To change a spec, edit the generator and
run `uv run python -m scripts.catalog_gen`. CI runs `--check` to catch hand edits and drift.

## API metadata conventions

Most teams put a standard block in `info.x-nordlys`:

```yaml
x-nordlys:
  api-id: claims-api
  domain: claims
  owner-team: claims-platform
  countries: [SE, "NO", FI, DK, EE, LV, LT]
  audience: internal            # internal | partner | channel-bff | restricted
  data-classification: personal
  lifecycle: {status: deprecated, deprecated-since: ..., sunset: 2026-12-31, replacement: claims-api v2}
```

Deprecated APIs also mark every operation `deprecated: true` and document the `Deprecation` and
`Sunset` response headers (RFC 9745 / RFC 8594).

## Data Product contract

Inspired by the Open Data Contract Standard, and validated by
`src/nordlys_discovery/catalog/models.py`:

| Section | Purpose |
|---|---|
| `owner` | accountable team, product owner role, support channel |
| `pii_classification` | `none` < `internal` < `personal` < `sensitive`, at product level and per field |
| `freshness` | update frequency, max delay, human-readable SLA |
| `schema` | fields with type, description and field-level PII |
| `quality_checks` | declarative checks (unique, range, accepted values, freshness, …) |
| `access` | OAuth scope, approval route, allowed and prohibited purposes, retention |
| `output_ports` | where to read it (Databricks table, Postgres view, Kafka topic, …) |
| `sample_rows` | synthetic example rows (later phases hide these for sensitive products) |

The model enforces some rules, and these are tested:

- A product's classification can never be weaker than its most sensitive field.
- `sensitive` products must require owner **and** DPO approval.
- Sample rows may only use declared columns.
- Unknown keys are rejected, so typos fail loudly.

## Deliberate realism (the "traps")

Real catalogs are messy. These imperfections are intentional, and the Phase 5 evaluation set tests
whether discovery handles them.

| Trap | Where | What good discovery should do |
|---|---|---|
| **Deprecated APIs (3)** | `quote-api` v1 (sunset 2026-11-15), `claims-api` v1 (2026-12-31), `policy-api` v1 (2027-03-31) | Never recommend v1 for new work; point to the replacement and give the sunset date |
| **Near-duplicates** | `claims-search-api` (claims-platform: search all claims by `status` + `country`) vs `claim-lookup-api` (digital-channels BFF: `state` + `market`, but **only the caller's own claims**) | For "all open claims in Norway", recommend claims-search-api and explain why the look-alike is wrong |
| **Undocumented spec** | `dk-document-archive-api` ("DKARKIV"): no descriptions or summaries, cryptic `getDoc1..3`, API-key auth, Danish field names (`polno`, `cpr`, `arkdato`) | Still findable from paths and schema names; flag the low documentation quality |
| **Legacy metadata** | `motor-policy-api` (Baltic, `x-owner`/`x-countries` as a comma string), `broker-commission-api` (finance) | Normalised by `metadata.py`, which records the provenance of each value |
| **Inconsistent writing** | Lower-case shorthand summaries (endorsements, fraud referrals, commission), Nordic-language terms (*skadeanmälan*, *forsikringsmeglere*), Markdown in some descriptions | Retrieval must not depend on one house style |
| **API vs data product overlap** | Open claims exist as an API (`claims-search-api`) and as a data product (`claims-open-cases-daily`) | Operational use → API; analytics or reporting → data product |
| **Restricted domains** | `fraud-signals-api`, `fraud-case-referral-api`, `claims-fraud-scores`, `health-claims-diagnosis` | Show metadata and how to request access; never leak sample data |
| **Partial market coverage** | `policy-endorsement-api` is SE and NO only; `travel-quote-api` is FI and SE only; `motor-telematics-trips` is SE and NO only | Answer "not available for DK" honestly |
